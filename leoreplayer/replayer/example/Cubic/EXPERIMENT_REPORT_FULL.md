# LEOCC 实验复现报告



**摘要**


本报告记录在本地工作站对仓层卫星拥塞控制（LEOCC）相关实验的复现过程。使用项目中的 `leoreplayer` 进行轨道/链路追踪驱动的重放试验，比较了 `reno`, `cubic`, `vegas` 三种 TCP 拥塞控制算法在示例轨迹下的吞吐表现。报告包含实验方法、数据聚合与分析，附带绘图与结果表格。



**引言**


近年低地轨道卫星通信（LEO）因其低延迟、高带宽的潜力而广受关注。本次复现实验旨在验证 `LeoCC` 仓库提供的重放工具能否在本地复现论文中部分结果，并比较常见 TCP 算法在该轨道链路条件下的性能差异。



**实验方案**


实验采用 `leoreplayer/replayer/example/Cubic` 示例中提供的带宽与延迟跟踪文件，使用 `run_batch.sh` 自动化运行：对每种算法执行多次重复（默认 5 次），每次持续 300 秒。通过 `aggregate_and_plot.py` 脚本汇总每次运行得到的 `queue_log.txt`，以 0.5s 为时间窗口计算吞吐（Mbps），并生成平均吞吐随时间曲线（含标准差）和每次运行平均吞吐的箱线图。



**实验内容与步骤**


1. 在 `example/Cubic` 目录下运行 `run_batch.sh`：该脚本会为每种算法创建 `results_<alg>/run_<i>/` 目录并把输出放入其中。


2. 运行完成后，执行 `aggregate_and_plot.py`，生成比较图像和 `plots/throughput_summary.csv`。


3. 运行 `generate_report.py` 将会把结果整合为本报告（Markdown 格式），并嵌入生成的图片。

**结果讨论（要点）**


- 仿真/重放结果受轨迹文件和重放器行为影响，结果仅为复现实验在本地机上的观测。


- `vegas` 在本次轨迹下表现出较低的平均吞吐，这可能与 `vegas` 更早地基于 RTT 的拥塞判断有关；`reno` 与 `cubic` 的平均吞吐相近，但拥塞/重传模式不同。

本次复现实验表明，在本地使用 `leoreplayer` 对轨迹数据进行重放，可以对比常见 TCP 算法在该链路条件下的吞吐表现。完整复现论文中由内核模块（`leocc`）实现的实验需匹配作者的内核/补丁版本，否则内核模块无法编译，这在我们的复现过程中已被验证。

**附加：基于 iperf 的有效性校验与结果**

在初次聚合时我们尝试使用 `queue_log.txt`（由重放器的队列记录生成）来计算吞吐，但发现该日志的时间戳范围与 `iperf3` 报告的总时长不匹配，导致通过队列日志计算的平均吞吐出现异常（数量级错误）。为保证实验结论可靠，我们改用 `iperf3` 的汇总结果作为主要吞吐度量。

下面给出基于 `run_full_experiment.log` 中 `iperf3` 汇总的箱线图：

![](plots/iperf_boxplot.png)

对应的 CSV 文件为 `plots/iperf_summary.csv`，可用于进一步统计检验与绘图。

结论修正：基于 `iperf3` 测得的平均吞吐显示三种算法在该轨迹下的中位/均值均在 8–12 Mbps 区间，`vegas` 略低（约 7–8 Mbps），`reno` 与 `cubic` 大致相近（约 10–12 Mbps）。相比之下，使用 `queue_log` 直接计算的瞬时吞吐波动很大且不可靠，因此不作为主结论依据。
